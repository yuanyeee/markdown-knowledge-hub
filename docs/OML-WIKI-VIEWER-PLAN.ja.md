# OML Wiki 閲覧画面の改善計画

1. 参照元と参照先を左右の方向として揃える。現行索引の文書リンクを「参照」として表示し、呼び出しの確定には別途根拠を保持する。図の選択ノードと矢印を強調する。
2. 元仕様書の見出しと要素ページの対応表を作り、一意に一致する見出しリンクを要素ページへ案内する。元仕様書リンクは原典への入口として残す。
3. 閲覧領域を高さ制約のある3枠にし、各枠を独立スクロールにする。管理フォームは折り畳み、選択ページ切替では中央だけ先頭へ戻す。
4. Mermaidをローカルに同梱し、厳格モードで遅延描画する。図に失敗した場合はコードと処理表で確認できるようにする。処理表から図を生成する場合は、行番号と次への列が揃った表に限定する。
5. RustとWebのテスト、Windowsビルド、反復操作時のメモリを確認する。WebView2の測定をバックエンドの測定と分けて記録する。

## 検証結果

- 合成データで元仕様書内の見出しリンクの振替、明示された呼び出しの方向と表示名、処理表からの図とMermaidブロックの描画を検証した。
- 左・中央・右の各枠で独立したスクロール設定を確認した。Mermaidは画像として表示し、切替時にBlob URLを解放する。
- 実仕様書を再生成し、仕様書327件、要素40,962件、一覧1件の計41,290ページを索引化した。処理フローの呼び出しリンクを21,906行出力した。重複を除いた呼び出し数やOML全体の網羅率は未計測。
- ChromiumでWikiと関係図を20往復した。5往復ごとのGC後JavaScriptヒープは合成データで14.3、15.5、15.7、15.7 MiB、41,290ページの索引で5.9、6.2、6.2、6.3 MiBだった。Wikiへの復帰ごとに関係図Canvasの解放を確認した。Windows WebView2全体の長時間メモリおよびGPUメモリは未計測。
- 呼び出し解決は明示された処理表の「アクション実行」行と、一意な要素名またはモジュール修飾名に対応する。見出しリンクの振替は同じ元仕様書内の一意なアンカーが対象。既存の生成済みWikiは元仕様書から再生成すると反映される。
